## 为什么要有一篇这样的东西

不是要教你 Markdown——那个十分钟就能学会。

真正的问题是**写技术笔记时该用哪种元素**。同一段内容，用列表还是表格、用引用还是加粗，读起来完全不一样。所以这篇文章的每一节，除了示范语法，还会说一句「什么时候用它」。

下面每一节的顺序，大致就是技术笔记里的使用频率。

## 标题层级

页面里用 `##` 作为一级小节（会出现在右侧目录里），`###` 作为二级小节，`####` 作为更细的分点。

#### 四级标题长这样

再往下的 `#####` 不建议使用，字号已经和正文接近了。

> **什么时候用**：一篇技术笔记 3~6 个 `##` 算正常。超过 10 个说明该拆成两篇了。目录面板是给人扫的，太长就失去意义。

## 行内样式

**加粗**、*斜体*、`行内代码`、~~删除线~~，以及 [站内链接](/index.html) 和 [外部链接](https://github.com/phantom726)。

站内链接写 `/index.html` 这种根路径就行，构建时会自动补成 `../index.html`。

外部链接会自动带上新窗口打开和 `rel="noopener"`，站内链接则走 P5 的擦除转场。

## 列表

无序列表：

- 第一项
- 第二项
  - 嵌套一层也没问题
- 第三项

有序列表会自动编号，并且用 P5 风格的斜体数字：

1. 先确定目标范围
2. 收集信息，列出所有入口
3. 逐个验证，记录证据
4. 整理成报告

> **什么时候用**：**有序列表 = 有先后顺序的步骤**（操作流程、排查顺序）；**无序列表 = 并列的要点**（特性、发现、注意事项）。
> 用错这个，读者会以为你写的要点是必须按顺序执行的。

## 引用

> 引用块会渲染成对话气泡的形状，右下角被切掉一块。
>
> 适合放警告、注意事项，或者需要被单独拎出来的结论。
>
> 多段引用也没问题。

> **什么时候用**：**需要读者"停下来想一下"的那一句**。全篇都用引用等于全篇都没有重点——一篇长文里有 2~4 处引用是合适的量。

## 代码

行内代码：`sqlmap -r req.txt --batch`。

代码块会自动高亮，左上角的标签会显示语言名：

```bash
# 时间盲注必须单线程，否则连不上
sqlmap -r req.txt -p id --technique=T --threads=1 --dbms=mysql
```

```python
import requests

def probe(url):
    """一个最小的探测脚本"""
    r = requests.get(url, timeout=5)
    return r.status_code, len(r.text)

if __name__ == '__main__':
    print(probe('http://127.0.0.1:8000/'))
```

```javascript
const slug = title
  .trim()
  .toLowerCase()
  .replace(/\s+/g, '-');
console.log(`posts/${slug}.html`);
```

代码块右上角有 COPY 按钮，点一下复制全文。

> **什么时候用**：**只要内容需要读者原样敲进终端，就用代码块**；只是提到某个命令名或参数名，用行内代码就够。
> 另外，语言名一定要写——不写的话程序会去猜，猜错比不高亮更难看。

## 表格

表头会自动变成红底白字：

| 工具 | 用途 | 常用参数 |
| --- | --- | --- |
| nmap | 端口与服务识别 | `-sV -sC -p-` |
| ffuf | 目录与参数爆破 | `-w dict -u URL/FUZZ` |
| sqlmap | SQL 注入检测 | `-r req.txt --batch` |
| Burp | 手工测试与改包 | — |

> **什么时候用**：**同一组属性在多个对象之间做横向对比**的时候。这是表格唯一不可替代的场景。
> 如果只有两列、行数也不多，写成「**名称** —— 说明」的列表反而更好读。表格列数超过 5 列在手机上会很挤。

## 图片

Markdown 图片语法，点一下会全屏放大：

```markdown
![描述文字](../assets/img/avatar.svg)
```

图片默认居中，带细边框和阴影。

> **注意**：文章在 `posts/` 下一层，引用站内图片要写 `../assets/...`；链接可以用 `/assets/...` 这种根路径，构建时会自动补。

## 任务清单

- [x] 已经完成的事
- [ ] 还没做的事
- [ ] 另一件没做的事

> **什么时候用**：适合「文末待办」或者一篇持续更新的长笔记。日常技术笔记里用得不多。

## 技术笔记的默认骨架

上面元素都摆了一遍，但**写技术笔记不需要全用**。这是一个够用的默认结构：

```
一句话结论（引用块）
  ↓
背景 / 前提（正文段落）
  ↓
操作步骤（有序列表 + 代码块）
  ↓
踩的坑（无序列表，或一张表格）
  ↓
参考 / 延伸（链接列表）
```

按这个骨架写，稿子至少有骨架、有重点、能扫读。剩下的是内容的事。

> 最后一句话：**排版是给"扫读"服务的**。没人会逐字读你的技术笔记，包括三个月后的你自己。所以让结构替你把重点顶出来。
