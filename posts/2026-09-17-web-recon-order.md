## 第 0 步：确认范围（这步跳过，后面全是白干）

动手之前先回答四个问题，写下来，不要只在脑子里过：

- **资产范围**：哪些 IP、哪些域名、哪些子域算数？
- **时间窗口**：允许在什么时间段测？
- **禁止动作**：能不能做拒绝服务类测试？能不能跑自动化爆破？
- **联系人**：出问题找谁、多久内必须报？

范围外的东西，看得见也不要碰。这不是胆小，这是执业底线——而且实战里客户最在意的就是这个。

> 下面所有命令里的地址都是靶场示例（`10.10.10.x` / `127.0.0.1`）。换到真实目标上，前提是第 0 步已经确认过范围。

## 第 1 步：被动收集（不碰目标，不产生流量）

先从公开信息里把轮廓拼出来，这一步**不会在目标日志里留下任何记录**：

| 目标 | 手段 |
| --- | --- |
| 域名归属 | `whois`、备案信息 |
| 子域名 | 证书透明日志（crt.sh 之类）、被动 DNS |
| 历史入口 | Wayback Machine 的历史快照 |
| 泄露信息 | GitHub 搜索、公开的配置文件 |
| 技术栈线索 | 招聘信息、公开文档里提到的技术 |

**历史快照特别值钱**：已经不挂在首页上的旧接口、旧后台路径，往往还活着，而且没人维护。这是被动阶段能挖到的最实用的东西。GitHub 上的密钥泄露同理——搜到的东西先确认是不是真的能用，别直接写进报告。

## 第 2 步：端口扫描，分三层做

最常见的错误是一条命令梭哈，`nmap -sV -sC -p- -T4` 一路跑到底。结果是慢得离谱，还容易被流量设备盯上。

**拆成三层，快很多：**

```bash
# 第一层：先看常见端口，30 秒内出结果
nmap -sS -T4 --top-ports 100 10.10.10.10

# 第二层：全端口，只看开不开，不做指纹
nmap -sS -p- --min-rate 2000 -n 10.10.10.10

# 第三层：只对已确认开放的端口做深挖
nmap -sV -sC -p 22,80,443,8080 10.10.10.10
```

**为什么这样拆**：

- 第一层让你**马上**知道这是个什么机器，可以并行去干别的事
- 第二层的目标只有一个：**有没有非标准端口在跑东西**。很多公司的运维后台就挂在 8443、9000 这类端口上
- 第三层才需要 `-sV -sC`，因为服务和脚本探测很慢，不值得对着 65535 个端口跑

**少用一个 `-A`**：它等于 `-sV -sC -O --traceroute` 全开，在真实目标上又慢又吵。知道自己在要什么，比开一堆选项有用。

**UDP 别忘**：`nmap -sU --top-ports 50 10.10.10.10`。SNMP（161）常常直接把整台设备的信息吐出来。

## 第 3 步：服务与框架指纹

```bash
whatweb -a 3 http://10.10.10.10
curl -sI http://10.10.10.10 | head -20
```

重点看几样东西：

- `Server` / `X-Powered-By` —— **有就直接记下来**，很多老系统会把版本号明明白白写在这儿
- 特殊 Cookie 名 —— 能反推出框架（不同的 Java 框架、PHP 框架各有特征）
- 404 页面的长相 —— 默认错误页本身就在告诉你这是什么框架
- 页脚、注释、`/robots.txt`、`/sitemap.xml`

**这一步的价值在于缩小范围**：知道是 Spring Boot 之后，你要翻的漏洞类型和要看的参数位置就完全不一样了。

## 第 4 步：目录与文件

```bash
ffuf -u http://10.10.10.10/FUZZ \
  -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -mc 200,301,302,403 -t 40
```

**403 和 401 跟 200 一样有价值。** 只匹配 200 会漏掉一半的信息——「存在但没权限」说明那里有东西，值得单独研究。

先手工试这几个，成本几乎为零：

```
/robots.txt        /sitemap.xml
/.git/config       /.svn/entries
/backup.zip        /www.zip        /web.rar
/index.php.bak     /config.php~
/admin             /manager         /console
```

**字典决定上限。** 用默认的 `common.txt` 扫一轮可以，但真正的东西往往在技术栈对应的专项字典里（比如 Struts2、Spring、WordPress 各有自己的路径表）。按第 3 步的指纹去选字典，比换更大的字典有效。

**注意速度**：`-t 40` 在本机靶场没问题，真实目标上先调到 10 以下试水。打崩目标服务是事故，不是成绩。

## 第 5 步：接口与参数

到了这一步，前面收集的东西开始连成线：

1. **从 JS 里翻接口**：前端打包文件里往往写着完整 API 路径和参数名。把 JS 全下来，搜 `/api/`、`token`、`key` 这类关键词
2. **从历史快照里翻旧接口**：前面第 1 步存下来的东西，在这里用
3. **从参数命名反推业务**：`?id=`、`?uid=`、`?file=`、`?url=` 这类参数的命名基本就在告诉你它下面是什么实现

到这一步你手上应该有一张表，而不是一堆截图。

## 第 6 步：整理，必须落到纸上

```
目标：10.10.10.10
------------------------------
端口   服务     版本              备注
22     ssh      OpenSSH 7.4       密码登录开着
80     http     nginx 1.18        跳到 /app
8080   http     Tomcat 9.0.30     默认管理页可达
------------------------------
发现：/backup.zip 可下载（含源码）
      /admin 返回 403
      历史快照里有 /api/v1/user?id=
```

> **信息收集是无限的，所以必须设时间盒。** 我的习惯是 30~40 分钟：到点就停下来，进入验证阶段。继续挖当然还能挖到东西，但边际收益会掉得很快——而且很多"线索"你不去验证，永远不知道是不是真的。

## 最后

信息收集最大的价值不是「找到更多东西」，是**让你在验证阶段不瞎猜**。

有这张表，你看到任何异常响应都能立刻对上上下文；没有这张表，你只是在碰运气。
