如果没有强制要求，大多数人打完比赛就散了。问题是一场比赛里真正学到的东西，大概 90% 会在一周内忘干净，剩下的只有「我好像做过一道这样的题」这种模糊印象。

所以判断一篇复盘合不合格，只有一个标准：三个月后的自己能不能靠它把同类型的题再做出来。

按这个标准，下面这些写法都不合格：

| 写法 | 问题 |
| --- | --- |
| 只贴 flag 和 payload | 没有思路，换个题就废 |
| 照着官方题解倒着抄一条干净路径 | 你没走过这条路，下次还是走不出来 |
| 写「这里过滤了空格所以用 `/**/` 绕过」 | 没说你是怎么发现被过滤的 |
| 长篇大论的情绪记录 | 三个月后你自己都不想看 |

## 一、还原时间线

这一步最烦，但最重要。打开比赛的聊天记录、提交记录、终端 history，把时间线拉出来：

```
00:00  开题，扫了一遍，Web 有两道
00:15  第一题看出是 SQLi，但手工测了十分钟没进展
00:25  上 sqlmap，跑了两分钟没结果，以为 WAF 挡了
00:40  换去啃第二题，卡在登录逻辑
01:10  回来手工测第一题，发现是过滤了逗号（不是我猜的空格）
01:35  出 flag
02:00  第二题始终没出来
```

要的不是结论，是你当时以为的是什么。上面这段里真正值钱的是 `00:25` 那行，「以为 WAF 挡了」是个错误判断，它直接让你浪费了 15 分钟还绕了远路。

这种事不写下来，下次还会犯。

## 二、给卡点分类

时间线上每个超过 10 分钟的卡点，都归到下面五类之一。分类这个动作本身就是在诊断。

| 类型 | 表现 | 下次怎么防 |
| --- | --- | --- |
| 知识缺口 | 完全不知道这个漏洞或算法是什么 | 补理论，写进知识清单 |
| 工具不熟 | 知道要干什么，但命令敲不对 | 把命令固化成脚本，写进速查表 |
| 思路错误 | 方向选错了，白走一大段 | 记下「错误的判断依据」，这才是重点 |
| 时间分配 | 在一道低分题上耗太久 | 设一个强制换题的时间阈值 |
| 环境问题 | 工具跑不起来、网络不通 | 赛前检查清单里补一条 |

我自己的情况是卡点基本都集中在第二类和第三类，第一类反而很少。漏洞学得少不是主要问题，动作不熟、判断不准才是。

想明白这点之后，练习的方向就变了：不是再刷 100 道题，而是把常用操作固化成脚本，把踩过的判断错误记下来。

## 三、写出错误的判断依据

这一步是整套流程里最特别的。对每个思路错误，问自己一句：我当时是根据什么得出那个结论的？

举两个例子：

- 看到 `?id=1'` 返回 500，我判断「有注入但语法错」
  - 实际是 WAF 拦了，返回页被改成了 500
  - 下次的判断依据：500 不一定是后端报错，先看响应体长度和服务器头，再下结论
- 看到响应时间变长，我判断「时间盲注可行」
  - 实际是网络抖动，多测三次就露馅了
  - 下次的判断依据：时间类判断必须重复三次取中位数

把「教训」翻译成「判断依据」，它才能被复用。「要多加小心」这种写法等于没写。

## 四、留下点东西

复盘结束的时候，至少留下下面某一样：

- 一条能直接抄的命令，进速查表
- 一个能自动跑的脚本
- 一条判断依据，进 checklist
- 一段原理说明，进知识库

什么都没有，说明这场复盘只是在抄题解。

## 附：我固定填的那张表

复制走直接用。

```markdown
## 题目信息
| 项目 | 内容 |
| --- | --- |
| 比赛 / 题目 / 分类 / 分值 |  |
| 结果 | 一血 / 解出 / 未解出 |
| 实际耗时 |  |

## 一句话结论
（说不出来说明还没真懂）

## 时间线
（含"当时以为的是什么"）

## 卡点分类
- 类型：
- 表现：
- 下次的判断依据：

## 利用过程
（按时间顺序，每步写清"为什么这么做"和"看到了什么"）

## 修复建议
1. 输入层：2. 执行层：3. 监控层：

## 沉淀
- [ ] 命令进速查表
- [ ] 判断依据进赛前检查清单
```

没解出来的题更要写，而且得写得更细。解出来的题你至少知道正确路径长什么样；没解出来的题，唯一的收获就是那份「我是怎么走错的」的记录，丢了就真的一无所获。

连着复盘五六场之后，赛前检查清单会自己长出来：

```
□ sqlmap 跑不出结果时，先确认是不是参数写错了，不要默认是 WAF
□ 时间类判断重复三次
□ 单题超过 40 分钟强制换题
□ 环境：sqlmap.bat 路径、代理、Python 版本
```

这份清单比题解更值得留着，因为它记的是你自己的毛病。
